## 1. Что вообще нового в этой лабе

До сих пор (лабы 1–4) UI строился только через **MVC**: контроллер → представление. В Лабе 5 добавляется **второй, параллельный сценарий** построения интерфейса — **Razor Pages** — специально для страниц администратора (CRUD над блюдами). Плюс — решается отдельная, независимая от Razor Pages задача: **как передать файл (картинку) от пользователя на сервер**, сохранить его в API-проекте на диске и правильно связать с объектом `Dish`.

Это две логически разные темы в одной лабе, поэтому и конспект разбит на два больших блока: сначала Razor Pages (раздел 3.1–3.3 методички), потом файлы (раздел 4).

## 2. Теория: Razor Pages

### 2.1. В чём отличие от MVC

В MVC у вас **один контроллер** обслуживает несколько связанных действий (`Index`, `Create`, `Edit`, `Delete` — всё в одном классе `ProductController`), а разметка лежит **отдельно** в `Views/Product/...`.

В Razor Pages для **каждой отдельной страницы** создаётся **пара файлов**, которые вместе образуют самодостаточный модуль:

```
Pages/Dishes/Index.cshtml      ← разметка страницы (Razor + HTML)
Pages/Dishes/Index.cshtml.cs   ← "код позади" (code-behind) — класс PageModel
```

Это тот же самый принцип, что был в старом WebForms/WPF (`.xaml` + `.xaml.cs`) — разметка и логика физически рядом, но в разных файлах.

| | MVC | Razor Pages |
|---|---|---|
| Точка входа | Метод `Action` в классе `Controller` | Отдельная страница `.cshtml` + класс `PageModel` в `.cshtml.cs` |
| Разметка и логика | Разнесены по разным папкам (`Controllers/` и `Views/`) | Лежат рядом, один рядом с другим, для одной и той же страницы |
| Что обрабатывает GET/POST | Разные методы (Actions) внутри одного контроллера, различаются по имени | Методы `OnGet`/`OnGetAsync`, `OnPost`/`OnPostAsync` **внутри одного и того же класса** `PageModel`, различаются по HTTP-методу, а не по имени |
| Маршрутизация | По шаблону `{controller}/{action}/{id?}`, настраивается централизованно в `Program.cs` | Маршрут **соответствует физическому пути файла** в папке `Pages/` (директива `@page` включает эту страницу в маршрутизацию) |
| Когда удобнее использовать | Когда у вас классический "ресурс" с типовым набором действий (списки, API) | Когда каждая страница — довольно самостоятельная "форма"/сценарий (админки, страницы регистрации, простые CRUD-формы) — Razor Pages по факту оптимизированы именно под сценарий "одна страница = одна задача" |

### 2.2. Класс `PageModel`

Каждая страница Razor Pages имеет "код позади" — класс, унаследованный от `PageModel`:

```csharp
public class IndexModel : PageModel
{
    private readonly IProductService _service;
    public IndexModel(IProductService service) => _service = service;

    public ListModel<Dish>? Data { get; set; }

    public async Task OnGetAsync(int pageNo = 1)
    {
        var resp = await _service.GetProductListAsync(null, pageNo);
        if (resp.Successfull) Data = resp.Data;
    }
}
```
(Файл: `labs/Areas/Admin/Pages/Dishes/Index.cshtml.cs`)

- `: PageModel` — базовый класс, дающий доступ к `ModelState`, `Page()`, `RedirectToPage()`, `User`, `Request`, `Response` и т.д. — то же самое, что `Controller` давал контроллерам в MVC, только для отдельной страницы.
- Конструктор с параметром `IProductService service` — **тот же самый механизм DI**, что и в контроллерах (раздел 1.3 файла `3.md`): фреймворк сам создаёт `PageModel` через DI-контейнер и подставляет туда зарегистрированный сервис.
- **Публичные свойства класса `PageModel` доступны прямо в разметке `.cshtml` через объект `Model`** — точно так же, как `@model` в обычном View, только тут модель — это сам класс страницы (свойства + методы), а не отдельный DTO.
- `OnGetAsync(int pageNo = 1)` — метод-обработчик **GET**-запроса к этой странице. Параметр `pageNo` заполняется Model Binding'ом из query string, точно так же, как параметры методов Action в MVC.
- **Соглашение по именам методов** — Razor Pages сама решает, какой метод вызвать, ориентируясь на HTTP-метод запроса и (опционально) значение атрибута `asp-page-handler`:
  - `OnGet` / `OnGetAsync` — обрабатывает `GET`.
  - `OnPost` / `OnPostAsync` — обрабатывает `POST`.
  - Можно иметь несколько именованных обработчиков на одной странице: `OnPostDeleteAsync`, `OnPostSaveAsync` — тогда в разметке форма должна указать `asp-page-handler="Delete"`, чтобы вызвать именно этот метод.

### 2.3. Директива `@page`

```cshtml
@page
@model labs.Areas.Admin.Pages.Dishes.IndexModel
```
(Файл: `labs/Areas/Admin/Pages/Dishes/Index.cshtml`)

- `@page` — **обязательная первая директива** любой Razor Page. Именно она превращает обычный `.cshtml`-файл в самостоятельную "страницу" со своим маршрутом (без неё файл считался бы обычным частичным представлением, недоступным напрямую по URL).
- `@page` может также принимать дополнительный шаблон маршрута: `@page "{id:int?}"` — добавляет ещё один сегмент URL сверх пути к файлу (см. вопрос №9 контрольных вопросов).
- `@model ...` — здесь работает так же, как в обычном Razor View, но указывает не произвольный DTO, а класс `PageModel` этой конкретной страницы. После этого в разметке доступен объект `Model`, представляющий экземпляр этого класса (со всеми его публичными свойствами).

### 2.4. Маршрутизация Razor Pages — от пути файла к URL

Ключевая идея: URL страницы Razor Pages **автоматически совпадает с её расположением на диске** относительно папки `Pages/` (для наших админ-страниц — относительно корня их Area, см. раздел 3):

| Файл | URL |
|---|---|
| `Pages/Dishes/Index.cshtml` | `/Dishes` (или `/Dishes/Index` — тоже работает, но каноничный — без `Index`, так как `Index` — имя "страницы по умолчанию" для папки, аналогично `index.html`) |
| `Pages/Dishes/Create.cshtml` | `/Dishes/Create` |
| `Pages/Dishes/Edit.cshtml` | `/Dishes/Edit` (с параметром `?id=5` или `/Dishes/Edit/5`, если добавлен шаблон маршрута) |

Никакой отдельной "таблицы маршрутов" (как `MapControllerRoute` для MVC) для каждой страницы писать не нужно — маршрутизация полностью определяется структурой файлов на диске. Единственное, что регистрируется централизованно в `Program.cs` — это сама поддержка механизма Razor Pages:
```csharp
builder.Services.AddRazorPages();
...
app.MapRazorPages();
```
(Файл: `labs/Program.cs`) — это **включает** Razor Pages вообще как технологию (как `AddControllersWithViews()`/`MapControllerRoute` включает MVC), но не описывает конкретные маршруты — те возникают автоматически по факту существования файлов.

### 2.5. Tag Helper `asp-page` (вместо `asp-controller`/`asp-action`)

В MVC для ссылок между страницами использовался `asp-controller`+`asp-action`. В Razor Pages — свой Tag Helper:

```cshtml
<a asp-page="Create" class="btn btn-primary">Create New</a>
...
<a asp-page="./Edit" asp-route-id="@item.Id" class="btn btn-success btn-sm">Edit</a>
```
(Файл: `labs/Areas/Admin/Pages/Dishes/Index.cshtml`)

- `asp-page="Create"` (или `asp-page="./Create"`) — указывает **имя страницы** (по сути — путь к файлу без расширения `.cshtml`), на которую нужно сослаться, а не "контроллер+экшен".
- `asp-route-id="@item.Id"` — работает точно так же, как в MVC: добавляет к сгенерированному URL параметр (`?id=5`, либо как сегмент пути, если он объявлен в шаблоне `@page "{id:int?}"`).
- **`"Create"` vs `"./Create"` vs `"/Create"`** (это прямо контрольный вопрос №8):
  - `Create` или `./Create` — **относительный** путь: страница ищется рядом с текущей, в той же папке.
  - `/Create` — **абсолютный** путь: страница ищется от **корня папки Pages** (или Area), а не от текущей.
  - На практике, пока все страницы лежат в одной папке `Dishes/`, разница не проявляется, но если бы страницы были в разных подпапках — `./Create` означало бы "Create рядом со мной", а `/Create` — "Create в самом корне".

## 3. Теория: Areas

**Area (область)** — способ разбить большое приложение на логически независимые "под-приложения", каждое со своей структурой `Controllers/Views/Pages`. У вас это уже встречалось в Лабе 2/3 при обсуждении пункта меню "Администрирование" — теперь эта Area реально реализуется.

Структура:
```
labs/
 └── Areas/
      └── Admin/                       ← имя области
           └── Pages/
                └── Dishes/
                     ├── Index.cshtml
                     ├── Index.cshtml.cs
                     ├── Create.cshtml
                     ├── Create.cshtml.cs
                     ├── Edit.cshtml
                     ├── Edit.cshtml.cs
                     ├── Details.cshtml
                     ├── Details.cshtml.cs
                     ├── Delete.cshtml
                     ├── Delete.cshtml.cs
                     ├── _ViewImports.cshtml
                     └── _ViewStart.cshtml
```
- Пространство имён классов страниц отражает физический путь: `labs.Areas.Admin.Pages.Dishes.IndexModel` — по этому пути видно: область `Admin`, папка страниц `Dishes`.
- URL для страниц внутри Area **дополнительно** включает сегмент `Admin`: например, страница `Areas/Admin/Pages/Dishes/Index.cshtml` доступна по адресу `/Admin/Dishes` (или `/Admin/Dishes/Index`) — то есть первым сегментом идёт имя Area.
- Чтобы Area с Razor Pages вообще заработала, ASP.NET Core должен "знать", что нужно искать страницы не только в `Pages/` (для не-Area случая), но и в `Areas/*/Pages/`. Для **Areas + Razor Pages** этот механизм включается автоматически вместе с `AddRazorPages()`/`MapRazorPages()` — никакой дополнительной регистрации Area для Razor Pages не требуется (в отличие от MVC-областей, где раньше нужен был отдельный маршрут `MapAreaControllerRoute`).

### 3.1. Свои `_ViewImports.cshtml` и `_ViewStart.cshtml` внутри Area

**Файл: `labs/Areas/Admin/Pages/Dishes/_ViewImports.cshtml`**
```cshtml
@using labs
@using labs.Models
@using labs.Domain.Entities
@addTagHelper *, Microsoft.AspNetCore.Mvc.TagHelpers
```

**Файл: `labs/Areas/Admin/Pages/Dishes/_ViewStart.cshtml`**
```cshtml
@{
    Layout = "_Layout";
}
```

Это **копии** файлов из основной папки `Views/` (задание методички прямо требует их скопировать: *"для использования страницы макета и базовых пространств имен в папку, в которой находятся страницы администратора, скопируйте файлы _ViewImports.cshtml и _ViewStart.cshtml"*). Причина: `_ViewImports.cshtml`/`_ViewStart.cshtml` действуют **только на файлы в своей папке и её подпапках** — папка `Areas/Admin/Pages/Dishes/` физически находится **вне** дерева `Views/`, поэтому общие файлы оттуда на неё не распространяются. Без собственных копий:
- не работали бы Tag Helpers (`asp-page`, `asp-for` и т.д.) — не был бы вызван `@addTagHelper`;
- не подключался бы общий `_Layout.cshtml` — каждая страница рендерилась бы "голой", без шапки/меню/футера сайта;
- не были бы доступны без полного имени классы `Dish`, `Category` (пришлось бы каждый раз писать `labs.Domain.Entities.Dish`).

## 4. Теория: передача файлов

### 4.1. Как браузер отправляет файл

Обычная HTML-форма (`application/x-www-form-urlencoded`) умеет передавать только **текстовые** пары "имя=значение". Чтобы передать **бинарные данные** (файл), форма должна явно объявить другой формат кодирования:

```html
<form method="post" enctype="multipart/form-data">
    ...
    <input asp-for="Image" type="file" class="form-control" />
    ...
</form>
```
(Файл: `labs/Areas/Admin/Pages/Dishes/Create.cshtml`)

- **`enctype="multipart/form-data"`** — обязательный атрибут (см. вопрос №15). Без него `<input type="file">` в браузере всё равно позволит выбрать файл, но при отправке формы содержимое файла **не попадёт** в тело запроса (в лучшем случае уйдёт только имя файла текстом).
- Формат `multipart/form-data` разбивает тело HTTP-запроса на несколько "частей" (parts), каждая — со своим именем поля и, для файлов, — с именем файла и содержимым в бинарном виде. Именно так можно в одном запросе передать **и текстовые поля формы, и один/несколько файлов одновременно**.

### 4.2. Как сервер принимает файл — интерфейс `IFormFile`

На стороне ASP.NET Core загруженный файл представлен объектом, реализующим интерфейс **`IFormFile`** (вопрос №11):

```csharp
[BindProperty]
public IFormFile? Image { get; set; }
```
(Файлы: `Create.cshtml.cs`, `Edit.cshtml.cs`)

- `IFormFile` — абстракция над загруженным файлом: содержит `FileName` (имя файла на компьютере пользователя), `ContentType` (MIME-тип), `Length` (размер в байтах), и метод `OpenReadStream()` / `CopyToAsync(...)` для чтения самого содержимого файла как потока байт.
- **`[BindProperty]`** — атрибут, который говорит Razor Pages: "заполни это свойство данными из входящего запроса (обычно — из тела `POST`-формы) автоматически, через Model Binding". Без этого атрибута свойство `PageModel` **не будет** автоматически связано с данными формы — это отличие от параметров метода-Action в MVC-контроллере, где привязка идёт по умолчанию: в Razor Pages для данных формы явно помечают именно **свойства класса**, а не параметры метода `OnPost`.
- Свойство названо `Image`, а на `<input>` стоит `asp-for="Image"` — Tag Helper `asp-for` генерирует атрибут `name="Image"` у `<input>`, и по этому имени срабатывает связывание с одноимённым свойством `[BindProperty]` на сервере.

### 4.3. Что происходит дальше с файлом — стратегия проекта

В вашем проекте выбрана следующая архитектура (это важно понимать целиком, потому что там участвуют **три** проекта):

```
Браузер                UI-проект (labs)             API-проект (labs.API)
--------                -----------------             ----------------------
<input type=file> --->  IFormFile Image        --->   [FromForm] IFormFile? file
(файл выбран              (получен через                (получен через ещё один
 пользователем)            Model Binding                 multipart/form-data —
                           в PageModel)                   UI-проект пересобирает
                                                           запрос и шлёт файл дальше
                                                           через HttpClient)
                                                                   |
                                                                   v
                                                       SaveImageHandler сохраняет
                                                       файл на диск в
                                                       labs.API/wwwroot/Images/
                                                       и возвращает URL картинки
```

Файл **дважды** проходит через сеть/уровни: сначала от браузера пользователя к UI-серверу (Razor Page получает `IFormFile`), затем UI-сервер **сам выступает клиентом** и пересылает этот файл дальше, в API-проект, через `HttpClient` (тоже используя `multipart/form-data`, но теперь уже как **клиент**, формирующий исходящий запрос). Именно поэтому изображение физически сохраняется в `labs.API/wwwroot/Images`, а не в `labs/wwwroot` — потому что именно API-проект работает с базой данных и "владеет" данными, а UI — лишь посредник, показывающий формы пользователю.

### 4.4. `IWebHostEnvironment` — доступ к `wwwroot`

```csharp
public class SaveImageHandler(
    IWebHostEnvironment env,
    IHttpContextAccessor httpContextAccessor)
    : IRequestHandler<SaveImage, string>
```
(Файл: `labs.API/Use-Cases/SaveImage.cs`)

- **`IWebHostEnvironment`** — сервис, зарегистрированный фреймворком автоматически (не нужно вручную регистрировать), даёт доступ к информации об окружении приложения: `env.WebRootPath` — **абсолютный физический путь** к папке `wwwroot` на диске сервера (см. вопрос №13), `env.ContentRootPath` — путь к корню проекта, `env.EnvironmentName` — "Development"/"Production" и т.д.
- Используется в коде:
  ```csharp
  var imagesFolder = Path.Combine(env.WebRootPath, "Images");
  ```
  — строит путь `<путь_к_wwwroot>/Images`, независимо от того, на какой ОС и в какой папке физически развёрнуто приложение (`Path.Combine` сам подставляет правильный разделитель `/` или `\`).

- **`IHttpContextAccessor`** — сервис, дающий доступ к текущему `HttpContext` **из мест, где он обычно недоступен напрямую** (например, из классов, которые не являются контроллером/страницей — как здесь, из обработчика MediatR). По умолчанию `HttpContext` доступен напрямую только внутри Controller/PageModel/Middleware; чтобы получить его в произвольном сервисе, нужно **явно зарегистрировать доступ** к нему:
  ```csharp
  builder.Services.AddHttpContextAccessor();
  ```
  (Файл: `labs.API/Program.cs`) — без этой строки `httpContextAccessor.HttpContext` всегда будет `null`.
  - Зачем он тут нужен: чтобы узнать текущий хост и протокол запроса (`https://localhost:7002`) и сформировать **полный, абсолютный URL** сохранённого изображения — а не просто относительный путь `Images/xxx.jpg` (это важно, потому что UI-проект и API-проект — это разные сервера/порты, и относительный путь на стороне UI указывал бы "не туда").

### 4.5. Случайное имя файла — зачем и как

```csharp
var extension = Path.GetExtension(request.File.FileName);
var fileName = $"{Guid.NewGuid()}{extension}";
```
(Файл: `labs.API/Use-Cases/SaveImage.cs`)

- Если сохранять файл под тем именем, которое было у него на компьютере пользователя (`request.File.FileName`), два разных пользователя, загрузившие файл `photo.jpg`, **перезапишут** файлы друг друга на сервере — это баг ("дублирование имён файлов" из задания).
- **`Guid.NewGuid()`** — генерирует случайный уникальный идентификатор (128-битное число, статистически гарантированно уникальное) в виде строки вроде `3fa85f64-5717-4562-b3fc-2c963f66afa6`.
- `Path.GetExtension(...)` — вытаскивает расширение исходного файла (`.jpg`, `.png` и т.д.), чтобы сохранённый файл на сервере имел то же расширение, что и исходный (важно для правильного отображения браузером и для MIME-типа при раздаче через `UseStaticFiles`).
- Итог: файл `photo.jpg`, загруженный пользователем, сохраняется на сервере как что-то вроде `3fa85f64-5717-4562-b3fc-2c963f66afa6.jpg` — гарантированно без конфликтов с другими файлами.

### 4.6. Сохранение потока на диск

```csharp
await using (var stream = new FileStream(filePath, FileMode.Create))
{
    await request.File.CopyToAsync(stream, cancellationToken);
}
```
- `FileStream(filePath, FileMode.Create)` — открывает (создаёт, если не было — или перезаписывает, если вдруг было) файл на диске по указанному пути для записи.
- `request.File.CopyToAsync(stream, ...)` — асинхронно копирует содержимое загруженного файла (`IFormFile`) в открытый поток файла на диске — то есть буквально "переливает" байты из входящего HTTP-запроса в файл на диске.
- `await using` — конструкция C# 8+, комбинирующая `await` и `using`: гарантирует, что `stream` будет корректно (и асинхронно) закрыт/освобождён после выполнения блока, даже если возникнет исключение — важно для файловых ресурсов, чтобы не "залипали" открытые дескрипторы файлов.

### 4.7. Удаление старого файла при замене/удалении объекта

Задание явно требует: *"При удалении объекта или при редактировании объекта, при замене изображения, предыдущий файл изображения должен удаляться."*

**Файл: `labs.API/EndPoints/DishEndpoints.cs`**, метод обновления (`MapPut`):
```csharp
if (file is not null)
{
    DeleteImageFile(existing.Image, env);
    existing.Image = await mediator.Send(new SaveImage(file));
}
```
- Если пользователь при редактировании **загрузил новый файл** (`file is not null`) — **сначала** удаляется старая картинка (`DeleteImageFile(existing.Image, env)`), **потом** сохраняется новая, и её URL записывается в `existing.Image`. Если новый файл не загружен — старое изображение просто остаётся без изменений (логика "менять только то, что явно прислано").

Метод удаления (`MapDelete`):
```csharp
DeleteImageFile(existing.Image, env);
db.Dishes.Remove(existing);
await db.SaveChangesAsync();
```
- При удалении объекта из БД — сначала удаляется связанный с ним файл картинки на диске, потом сама запись из базы (иначе файл остался бы "осиротевшим" — занимал бы место на диске, но ни на что не ссылался).

Сам вспомогательный метод:
```csharp
private static void DeleteImageFile(string? imageUrl, IWebHostEnvironment env)
{
    if (string.IsNullOrWhiteSpace(imageUrl)) return;
    try
    {
        var path = imageUrl.Contains("://")
            ? new Uri(imageUrl).LocalPath
            : imageUrl.Replace('/', Path.DirectorySeparatorChar);
        var fileName = Path.GetFileName(path);
        if (string.IsNullOrEmpty(fileName)) return;
        var imagesFolder = Path.Combine(env.WebRootPath, "Images");
        var fullPath = Path.GetFullPath(Path.Combine(imagesFolder, fileName));
        if (!fullPath.StartsWith(Path.GetFullPath(imagesFolder))) return; // защита от выхода за пределы папки
        if (File.Exists(fullPath)) File.Delete(fullPath);
    }
    catch { /* удаление — необязательная операция, ошибку игнорируем */ }
}
```
- Так как `Dish.Image` хранится как **полный URL** (`https://localhost:7002/Images/xxx.jpg`), а не просто имя файла — сначала нужно достать из него именно **имя файла** (`Path.GetFileName`), отбросив адрес хоста и путь.
- `Path.GetFullPath(...)` + проверка `StartsWith(...)` — защитная мера: не дать значению `Image` (если оно вдруг окажется некорректным, например будет содержать `../../etc/passwd`) "вывести" операцию удаления **за пределы** папки `Images` — классическая защита от атаки Path Traversal.
- `try/catch` с пустым `catch` — сознательное решение: если что-то пошло не так при удалении файла (файла уже нет, нет прав и т.п.) — это не должно "уронить" всю операцию удаления/обновления объекта в базе данных; удаление файла на диске считается второстепенной, не критичной для целостности данных операцией.

## 5. Общая схема: путь файла от браузера до диска

Разберём весь путь на примере **создания** нового блюда с картинкой (`Create.cshtml` → `Create.cshtml.cs` → `ApiProductService.CreateProductAsync` → `labs.API` → диск):

1. **Браузер**: пользователь на странице `/Admin/Dishes/Create` заполняет форму и выбирает файл в `<input type="file" asp-for="Image">`. Нажимает "Create" → форма с `enctype="multipart/form-data"` отправляет `POST` на `/Admin/Dishes/Create`.
2. **Razor Page (`CreateModel.OnPostAsync`)**: Model Binding заполняет `[BindProperty] public Dish Dish` (текстовые поля формы) и `[BindProperty] public IFormFile? Image` (файл). Проверяется `ModelState.IsValid`.
3. Вызывается `await _service.CreateProductAsync(Dish, Image);` — `_service` это `IProductService`, реально подставляется `ApiProductService` (зарегистрирован через `AddHttpClient` — см. `4.md`).
4. **`ApiProductService.CreateProductAsync`**: собирает **новый** `multipart/form-data` запрос (см. раздел 8 ниже) — кладёт туда файл (`formFile.OpenReadStream()`) под именем `"file"` и сериализованный в JSON объект `Dish` под именем `"dish"`, отправляет `POST` на API (`https://localhost:7002/api/dish/`).
5. **API (`DishEndpoints.MapPost`)**: принимает данные через `[FromForm] string dish` (JSON-строка) и `[FromForm] IFormFile? file` (файл), десериализует `dish` в объект `Dish`.
6. Если файл есть — отправляет **MediatR-команду** `new SaveImage(file)` → её обрабатывает `SaveImageHandler`.
7. **`SaveImageHandler`**: генерирует случайное имя, сохраняет байты файла на диск в `labs.API/wwwroot/Images/`, возвращает **полный URL** файла (`https://localhost:7002/Images/xxxxx.jpg`).
8. Этот URL записывается в `newDish.Image`, объект `Dish` сохраняется в базу через EF Core (`db.Dishes.Add(newDish); await db.SaveChangesAsync();`).
9. API отвечает `201 Created` с созданным объектом.
10. `ApiProductService` разбирает ответ, `CreateModel.OnPostAsync` делает `RedirectToPage("./Index")` — пользователь возвращается на список, где уже видит новое блюдо с картинкой (так как `Image` в базе — уже готовый абсолютный URL, `<img src="@item.Image">` в `Index.cshtml` отображает его напрямую, без дополнительной обработки).

### 6.2. `Create.cshtml` + `Create.cshtml.cs` — создание

**`labs/Areas/Admin/Pages/Dishes/Create.cshtml.cs`**
```csharp
public class CreateModel : PageModel
{
    private readonly IProductService _service;
    private readonly ICategoryService _categories;

    public CreateModel(IProductService service, ICategoryService categories)
    {
        _service = service;
        _categories = categories;
    }

    public async Task<IActionResult> OnGetAsync()
    {
        await LoadCategoriesAsync();
        return Page();
    }

    [BindProperty]
    public Dish Dish { get; set; } = default!;

    [BindProperty]
    public IFormFile? Image { get; set; }

    public async Task<IActionResult> OnPostAsync()
    {
        if (!ModelState.IsValid)
        {
            await LoadCategoriesAsync();
            return Page();
        }
        await _service.CreateProductAsync(Dish, Image);
        return RedirectToPage("./Index");
    }

    private async Task LoadCategoriesAsync()
    {
        var resp = await _categories.GetCategoryListAsync();
        var list = resp.Successfull && resp.Data is not null ? resp.Data : new List<Category>();
        ViewData["CategoryId"] = new SelectList(list, "Id", "Name");
    }
}
```
- **`OnGetAsync()`** — вызывается при **первом открытии** страницы (пользователь ещё ничего не отправлял): нужно только показать пустую форму, но список категорий для выпадающего `<select>` уже нужно загрузить — вызывается `LoadCategoriesAsync()`, затем `return Page();`.
- **`Page()`** — метод базового класса `PageModel`, аналог `View()` в контроллере: говорит "отрендери разметку **этой же** страницы" (в отличие от `RedirectToPage`, который отправляет браузер на **другую** страницу отдельным новым запросом).
- **`OnPostAsync()`** — вызывается при отправке формы. Сначала проверяется `ModelState.IsValid` — встроенная проверка валидации (на основе data-аннотаций на классе `Dish`, если они там есть, и базовых проверок типов при связывании). Если данные некорректны — **важно**: категории нужно загрузить **заново** (`LoadCategoriesAsync()`), потому что при повторном показе формы с ошибками `<select>` иначе окажется пустым (Model Binding не восстанавливает список опций сам — это чисто "справочные" данные, не часть отправленной формы).
- `await _service.CreateProductAsync(Dish, Image);` — здесь `Dish` и `Image` — это свойства **самого `PageModel`**, уже заполненные Model Binding'ом из тела запроса.
- `return RedirectToPage("./Index");` — аналог `RedirectToAction` из MVC, только адресует не Controller/Action, а страницу Razor Pages по её пути.
- `LoadCategoriesAsync()` — приватный вспомогательный метод (не является обработчиком `OnGet`/`OnPost`, поэтому вызывается вручную оттуда, где нужен), заполняет `ViewData["CategoryId"]` объектом `SelectList` — тем самым механизмом, что уже разбирался в `3.md` (Лаба 2, `asp-items`).

### 6.3. `Edit.cshtml` + `Edit.cshtml.cs` — редактирование

**`labs/Areas/Admin/Pages/Dishes/Edit.cshtml.cs`**
```csharp
public class EditModel : PageModel
{
    ...
    [BindProperty]
    public Dish Dish { get; set; } = default!;

    [BindProperty]
    public IFormFile? Image { get; set; }

    public async Task<IActionResult> OnGetAsync(int? id)
    {
        if (id is null) return NotFound();
        var resp = await _service.GetProductByIdAsync(id.Value);
        if (!resp.Successfull || resp.Data is null) return NotFound();
        Dish = resp.Data;
        await LoadCategoriesAsync();
        return Page();
    }

    public async Task<IActionResult> OnPostAsync(int id)
    {
        if (!ModelState.IsValid)
        {
            await LoadCategoriesAsync();
            return Page();
        }
        await _service.UpdateProductAsync(id, Dish, Image);
        return RedirectToPage("./Index");
    }
    ...
}
```
- `OnGetAsync(int? id)` — при **открытии** страницы редактирования, `id` приходит как параметр запроса (в URL `/Admin/Dishes/Edit?id=5`), находит объект через `_service.GetProductByIdAsync(id.Value)` и **заполняет им** свойство `Dish` — то есть форма при открытии показывает уже заполненные текущими значениями поля (в отличие от `Create`, где `Dish` остаётся пустым по умолчанию).
- `id is null` / `!resp.Successfull` — двойная защита: если `id` не передан или объект с таким `id` не найден — сразу `NotFound()` (HTTP 404), без попытки рендерить страницу редактирования "ничего".
- `OnPostAsync(int id)` — при **отправке** формы `id` уже **обязательный, не nullable** параметр (`int`, а не `int?`) — предполагается, что раз дошли до сохранения, id должен быть валиден (обычно передаётся скрытым полем формы, см. ниже).
- `_service.UpdateProductAsync(id, Dish, Image)` — обратите внимание: сигнатура интерфейса `IProductService.UpdateProductAsync` возвращает `Task` (не `Task<ResponseData<...>>`) — то есть в отличие от `Create`, эта операция **не возвращает** созданный/обновлённый объект, только выполняется.

**`labs/Areas/Admin/Pages/Dishes/Edit.cshtml`** — ключевые отличия от `Create.cshtml`:
```cshtml
<input type="hidden" asp-for="Dish.Id" />
<input type="hidden" asp-for="Dish.MimeType" />
...
<div class="form-group">
    <label class="control-label">Текущее изображение</label>
    <div>
        @if (!string.IsNullOrEmpty(Model.Dish.Image))
        {
            <img src="@Model.Dish.Image" alt="@Model.Dish.Name" width="200" class="img-thumbnail" />
        }
        else
        {
            <span class="text-muted">Нет изображения</span>
        }
    </div>
</div>
<div class="form-group">
    <label asp-for="Image" class="control-label"></label>
    <input asp-for="Image" type="file" class="form-control" />
</div>
```
- `<input type="hidden" asp-for="Dish.Id" />` — **скрытое** поле формы: пользователь его не видит и не редактирует, но оно всё равно передаётся при отправке формы, обеспечивая, что `Id` редактируемого объекта дойдёт до `OnPostAsync` через Model Binding (наряду с явным параметром `id` в самом URL — задание сохраняет `Id` "с двух сторон" для надёжности).
- Блок "текущее изображение" — это и есть пункт задания 4.5.1 ("необязательно: при редактировании выводить текущее изображение объекта") — показывает уже сохранённую картинку **до** того, как пользователь, возможно, выберет новую для замены. Поле `<input type="file">` при этом **не** предзаполняется файлом (это невозможно технически по соображениям безопасности браузеров — JS/сервер не может "подставить" файл в `<input type="file">"), так что если пользователь ничего не выберет — `Image` на сервере придёт `null`, и `UpdateProductAsync`/`DishEndpoints.MapPut` (см. раздел 4.7) корректно оставит старую картинку без изменений.

```csharp
        if (id is null) return NotFound();
        var resp = await _service.GetProductByIdAsync(id.Value);
        if (!resp.Successfull || resp.Data is null) return NotFound();
        Dish = resp.Data;
        return Page();
    }
}
```
- Заметьте: свойство `Dish` здесь **без** `[BindProperty]` — потому что эта страница только **показывает** данные, ничего не отправляет обратно на сервер (нет `<form>` с полями ввода), поэтому Model Binding для записи сюда не нужен, `Dish` заполняется вручную кодом.
- В разметке (`Details.cshtml`) используются хелперы `@Html.DisplayNameFor(model => model.Dish.Name)` и `@Html.DisplayFor(model => model.Dish.Name)` — стандартные сгенерированные скаффолдом хелперы: `DisplayNameFor` выводит подпись поля (из атрибутов `[Display(Name = "...")]`, если есть, иначе — имя свойства), `DisplayFor` выводит само значение с учётом формата отображения. Это чисто автоматически сгенерированный код шаблона "Details" — можно было бы написать и просто `@Model.Dish.Name`, разницы для вас на защите функционально нет, но стоит знать, что это стандартный Razor-хелпер для "только чтения" отображения свойств модели.

### 6.5. `Delete.cshtml` / `Delete.cshtml.cs` — удаление

```csharp
public class DeleteModel : PageModel
{
    private readonly IProductService _service;
    public DeleteModel(IProductService service) => _service = service;

    [BindProperty]
    public Dish Dish { get; set; } = default!;

    public async Task<IActionResult> OnGetAsync(int? id)
    {
        if (id is null) return NotFound();
        var resp = await _service.GetProductByIdAsync(id.Value);
        if (!resp.Successfull || resp.Data is null) return NotFound();
        Dish = resp.Data;
        return Page();
    }

    public async Task<IActionResult> OnPostAsync(int? id)
    {
        if (id is null) return NotFound();
        await _service.DeleteProductAsync(id.Value);
        return RedirectToPage("./Index");
    }
}
```
- Двухшаговый сценарий: `OnGetAsync` — просто **показать** объект и спросить подтверждение ("Are you sure you want to delete this?"); `OnPostAsync` — уже **реально** удалить, когда пользователь нажал кнопку в форме подтверждения.
- Заметьте: `Dish` здесь **с** `[BindProperty]`, хотя, казалось бы, при удалении не нужны все поля формы — это сделано только чтобы через скрытое поле `<input type="hidden" asp-for="Dish.Id" />` при `POST` надёжно вернулся `Id`. По факту `OnPostAsync` использует **параметр** `id` из URL, а не `Dish.Id` — но `[BindProperty]` на всём объекте `Dish` — это просто "по шаблону" скаффолда, реально расходуется в основном `Dish.Id` через скрытое поле, остальные поля `Dish` в `OnPostAsync` не используются.
- `<form method="post">` — **без** `enctype="multipart/form-data"` (файл тут не передаётся, только `Id`), и **без** `asp-page`/`asp-route-*` в самой форме — по умолчанию форма отправляется на тот же URL, с которого была получена (то есть на `Delete?id=5`).

### 6.6. Все страницы разом — общий паттерн

Обратите внимание, что во **всех пяти** страницах повторяется один и тот же скелет:
1. `PageModel` получает через DI нужные сервисы (`IProductService`, иногда `ICategoryService`).
2. `OnGetAsync` — подготовка данных для отображения (получить список/объект, проверить на `null`/ошибку → `NotFound()`).
3. `OnPostAsync` (только там, где есть форма — `Create`, `Edit`, `Delete`) — обработка отправленных данных, вызов соответствующего метода сервиса, `RedirectToPage("./Index")` в случае успеха.

Это классический паттерн **PRG (Post/Redirect/Get)**: после успешной обработки `POST`-запроса сервер не рендерит страницу напрямую, а **перенаправляет** браузер (HTTP 302 + новый `GET`-запрос) — так что при обновлении страницы (F5) браузер не переотправит форму повторно (частая причина случайного дублирования данных, если не использовать этот паттерн).

## 7. Построчный разбор серверной части сохранения файла

### 7.1. Use-Case `SaveImage` — паттерн MediatR (уже знаком по `4.md`)

**Файл: `labs.API/Use-Cases/SaveImage.cs`**
```csharp
public sealed record SaveImage(IFormFile File) : IRequest<string>;
```
- Точно тот же паттерн, что и `GetListOfProducts` из Лабы 4 (`4.md`, раздел "Блок 4"): `record`, реализующий `IRequest<T>` — "сообщение-запрос", несущее в себе всё необходимое (тут — сам загруженный файл), с указанием, что ответ будет строкой (`IRequest<string>` — это будет URL сохранённого файла).
- `sealed` — класс не может быть унаследован далее (обычная практика для таких небольших неизменяемых "сообщений").

```csharp
public class SaveImageHandler(
    IWebHostEnvironment env,
    IHttpContextAccessor httpContextAccessor)
    : IRequestHandler<SaveImage, string>
{
    public async Task<string> Handle(SaveImage request, CancellationToken cancellationToken)
    {
        ...
        return $"{baseUrl}/Images/{fileName}";
    }
}
```
- `IRequestHandler<SaveImage, string>` — "обработчик" для сообщения `SaveImage`, возвращающий `string`. MediatR сам находит этот класс по совпадению типа (никакой ручной регистрации не нужно, кроме общей строчки `AddMediatR(...)` в `Program.cs`, которая сканирует всю сборку на такие классы).
- Конструктор записан в **сокращённом синтаксисе (primary constructor, C# 12)**: `public class SaveImageHandler(IWebHostEnvironment env, IHttpContextAccessor httpContextAccessor) : ...` — это то же самое, что писать обычный конструктор с полями, просто короче; параметры `env` и `httpContextAccessor` автоматически становятся доступны во всех методах класса, как если бы были приватными полями.
- Вызывается это извне так: `await mediator.Send(new SaveImage(file));` (см. `DishEndpoints.cs`) — Endpoint/контроллер **не знает**, как именно сохраняется файл (на диск? в облако? в БД как blob?) — вся эта логика полностью инкапсулирована в `SaveImageHandler`, что позволяет позже сменить способ хранения файлов, не трогая код Endpoint'ов.

### 7.2. `DishEndpoints.cs` — интеграция с MediatR и Model Binding файлов в Minimal API

```csharp
group.MapPost("/", async (
    [FromForm] string dish,
    [FromForm] IFormFile? file,
    AppDbContext db,
    IMediator mediator) =>
{
    var newDish = JsonSerializer.Deserialize<Dish>(dish);
    if (newDish is null) return Results.BadRequest("Некорректные данные блюда");

    if (file is not null)
    {
        newDish.Image = await mediator.Send(new SaveImage(file));
    }

    db.Dishes.Add(newDish);
    await db.SaveChangesAsync();
    return TypedResults.Created($"/api/Dish/{newDish.Id}", newDish);
})
.WithName("CreateDish");
```
- **`[FromForm] string dish`** — в отличие от обычных Minimal API методов (`4.md`, где данные брались из `[FromBody]` как чистый JSON), здесь данные объекта передаются **как часть формы** — потому что весь запрос целиком имеет тип `multipart/form-data` (из-за файла), а не `application/json`. Поэтому сам объект `Dish` передаётся не напрямую как JSON-тело, а как **одно из текстовых полей формы** (`"dish"`), в котором лежит JSON-строка — и её приходится **вручную десериализовать**: `JsonSerializer.Deserialize<Dish>(dish)`.
- **`[FromForm] IFormFile? file`** — соответствующее поле `"file"` формы, содержащее сами байты изображения.
- **`.DisableAntiforgery()`** (см. `group = routes.MapGroup("/api/Dish").DisableAntiforgery();`) — обязательная настройка (задание прямо требует её добавить). По умолчанию ASP.NET Core **требует** anti-forgery токен для любых данных формы (`[FromForm]`), потому что это одна из стандартных защит от CSRF-атак (Cross-Site Request Forgery) для форм браузера. Но для API, которое вызывается **программно** (нашим `HttpClient`-сервисом, а не напрямую браузерной формой с CSRF-токеном внутри), такой токен взять неоткуда — и его проверку явно отключают именно для этой группы маршрутов API.
- `TypedResults.Created($"/api/Dish/{newDish.Id}", newDish)` — стандартный REST-ответ **201 Created**, включающий в заголовке `Location` адрес созданного ресурса и сам объект в теле — общепринятая практика для успешного `POST`, создающего новую запись.

Метод `MapPut` (обновление) устроен аналогично, только дополнительно вызывает `DeleteImageFile(...)` перед перезаписью (раздел 4.7), а `MapDelete` — только удаляет файл и запись, без работы с MediatR/`SaveImage`.

## 8. Построчный разбор клиентской части

### 8.1. `ApiProductService.CreateProductAsync` — сборка запроса с файлом

**Файл: `labs/Services/ProductService/ApiProductService.cs`**
```csharp
public async Task<ResponseData<Dish>> CreateProductAsync(Dish product, IFormFile? formFile)
{
    product.Image = "Images/noimage.jpg";

    var request = new HttpRequestMessage
    {
        Method = HttpMethod.Post,
        RequestUri = _httpClient.BaseAddress
    };

    var content = new MultipartFormDataContent();

    if (formFile != null)
    {
        var streamContent = new StreamContent(formFile.OpenReadStream());
        content.Add(streamContent, "file", formFile.FileName);
    }

    var data = new StringContent(JsonSerializer.Serialize(product));
    content.Add(data, "dish");

    request.Content = content;

    var response = await _httpClient.SendAsync(request, CancellationToken.None);
    ...
}
```
- `product.Image = "Images/noimage.jpg";` — сначала объекту "по умолчанию" ставится заглушка-картинка ("нет изображения"); если файл реально прислан и успешно сохранён на сервере API — значение `Image` всё равно **перезапишется** уже на стороне сервера (`newDish.Image = await mediator.Send(new SaveImage(file));`) настоящим URL — то есть значение, выставленное здесь на клиенте, играет роль лишь "на случай, если файла нет вообще".
- **`MultipartFormDataContent`** — класс из `System.Net.Http`, представляющий тело запроса `multipart/form-data` **на стороне клиента** (то есть UI-проект здесь ведёт себя как "браузер", формирующий такую же по формату форму, только программно, не через HTML).
- `content.Add(streamContent, "file", formFile.FileName)` — добавляет "часть" с именем поля `"file"` (это то самое согласованное имя — вспомните "Соглашение об именовании: … предлагается использовать имя `file`" из задания методички) и содержимым — потоком байт исходного файла, полученного от браузера в Razor Page.
- `content.Add(data, "dish")` — добавляет вторую часть, с именем `"dish"`, содержащую **JSON-строку** сериализованного объекта `Dish` — это и есть то самое поле `[FromForm] string dish`, которое принимает `DishEndpoints.MapPost` в API-проекте (раздел 7.2).
- `_httpClient.SendAsync(request, ...)` — низкоуровневая отправка полностью собранного `HttpRequestMessage` (в отличие от `_httpClient.GetAsync(url)`, используемого для простого `GET` без файла в `GetProductListAsync` — там достаточно готового вспомогательного метода, а тут нужен полный контроль над телом запроса).

## 10. Саммари для защиты

- **Суть лабы:** добавили в UI-проект **второй способ построения интерфейса** — Razor Pages (страницы админки в `Areas/Admin/Pages/Dishes`), параллельно к уже существующему MVC-каталогу. Плюс реализовали полноценную передачу файлов (изображений блюд) от браузера до диска сервера.
- **Razor Pages vs MVC:** страница = разметка (`.cshtml`) + код (`.cshtml.cs`, класс `PageModel`), лежат рядом, маршрут определяется физическим путём файла, HTTP-методы (`GET`/`POST`) различаются по имени метода (`OnGet`/`OnPost`), а не отдельными Action.
- **Areas:** позволяют выделить логически отдельную часть приложения (админку) со своей структурой страниц; для правильной работы Layout/Tag Helpers нужно скопировать `_ViewImports.cshtml`/`_ViewStart.cshtml` в папку страниц Area.
- **Файлы:** передаются через `<form enctype="multipart/form-data">` → сервер получает их как `IFormFile` (через `[BindProperty]` в Razor Pages). UI-проект **сам как клиент** пересобирает `multipart/form-data`-запрос (`MultipartFormDataContent`) и пересылает файл дальше в API. API сохраняет файл на диск в `wwwroot/Images` под случайным именем (`Guid.NewGuid()`), используя `IWebHostEnvironment` для пути и `IHttpContextAccessor` для формирования абсолютного URL, и возвращает этот URL, который записывается в `Dish.Image`.
- **MediatR снова в деле:** логика сохранения файла инкапсулирована в отдельный Use-Case (`SaveImage`/`SaveImageHandler`) — Endpoint не знает деталей реализации сохранения, только отправляет запрос через `mediator.Send(...)`.
- **Удаление файлов:** при замене изображения или удалении объекта старый файл на диске удаляется явно (`DeleteImageFile`), чтобы не копились "осиротевшие" файлы.
- **Antiforgery:** для программных (не-браузерных) вызовов API с формами (`[FromForm]`) нужно явно отключать проверку anti-forgery токена через `.DisableAntiforgery()` на группе маршрутов.

## 11. Ответы на контрольные вопросы

**1) Чем сценарий Razor Pages отличается от MVC?**
В MVC один контроллер обслуживает несколько связанных действий, а разметка вынесена отдельно в `Views/`. В Razor Pages каждая страница самодостаточна: разметка (`.cshtml`) и код (`.cshtml.cs` — класс `PageModel`) лежат рядом, друг для друга, а маршрут страницы определяется её физическим расположением в файловой системе (директива `@page`), а не централизованным шаблоном маршрута.

**2) Что такое модель страницы Razor?**
Класс, унаследованный от `PageModel` (например, `IndexModel : PageModel`), содержащий данные (публичные свойства, доступные в разметке через `Model`) и методы-обработчики HTTP-запросов (`OnGet`/`OnPost` и их асинхронные варианты) для конкретной страницы. Указывается в разметке директивой `@model`.

**3) Как обрабатываются запросы к страницам Razor?**
По HTTP-методу запроса вызывается соответствующий метод модели страницы: `GET` → `OnGet`/`OnGetAsync`, `POST` → `OnPost`/`OnPostAsync` (можно иметь несколько именованных обработчиков через `OnPost<Имя>`/`asp-page-handler`). Параметры методов (или свойства с `[BindProperty]`) заполняются через Model Binding из query string/route/form data — так же, как для Actions в MVC.

**4) Как в разметке страницы Razor получить доступ к свойствам модели страницы?**
Через специальный объект `Model`, доступный после объявления `@model ТипМодели` — например, `@Model.Data`, `Model.Dish.Name`.

**5) Как привязать данные формы к модели страницы?**
Пометить нужное свойство класса `PageModel` атрибутом `[BindProperty]` (например, `[BindProperty] public Dish Dish { get; set; }`), а в разметке связать элементы формы с этим свойством через Tag Helper `asp-for` (`<input asp-for="Dish.Name" />`) — тогда при `POST`-запросе Model Binding автоматически заполнит свойство данными формы.

**6) Для чего используется директива `@page`?**
Обязательная первая директива, превращающая обычный `.cshtml`-файл в самостоятельную Razor Page — включает её в маршрутизацию (URL соответствует пути файла) и позволяет ей иметь собственную модель (`PageModel`). Опционально может задавать дополнительный сегмент маршрута: `@page "{id:int?}"`.

**7) Какой Url будет у страницы Register на рисунке?**
Судя по расположению файла (`Areas/Identity/Pages/Account/Register.cshtml`), URL будет `/Identity/Account/Register` — первый сегмент — имя области (Area) `Identity`, далее — путь внутри `Pages/` этой области (`Account/Register`), без расширения `.cshtml`.

**8) Чем отличается адрес страницы «/index» от «./index»?**
`/index` — **абсолютный** путь: страница ищется от корня папки `Pages` (или корня текущей Area). `./index` — **относительный** путь: страница ищется в той же папке, что и текущая (та, откуда стоит ссылка). Если все страницы лежат в одной папке — разницы на практике нет, но при разнесении по подпапкам это важно: `./index` "переедет" вместе со страницей при перемещении по структуре, а `/index` — жёстко привязан к корню.

**9) Как указать дополнительный сегмент маршрута к странице (например, id)?**
В директиве `@page` указать шаблон маршрута прямо строкой: `@page "{id:int?}"` — тогда, помимо стандартного пути к странице, в URL можно будет передать ещё и `id` как часть пути (`/Dishes/Edit/5`), а не только как query-параметр (`?id=5`). `:int` — ограничение типа параметра, `?` — необязательность параметра.

**10) Какой Middleware используется для передачи статического контента клиенту?**
`app.UseStaticFiles()` (либо, в новых версиях ASP.NET Core, `app.MapStaticAssets()`) — раздаёт файлы из папки `wwwroot` (и её подпапок, например `wwwroot/Images`) напрямую по HTTP-запросу, без дополнительной обработки контроллером.

**11) Какой интерфейс реализует объект, полученный сервером, при передаче файла от клиента на сервер?**
`IFormFile` — представляет загруженный через форму файл: даёт доступ к его имени (`FileName`), MIME-типу (`ContentType`), размеру (`Length`) и содержимому (через `OpenReadStream()`/`CopyToAsync(...)`).

**12) Что такое поставщики файлов (FileProvider)?**
`IFileProvider` — абстракция ASP.NET Core для доступа к файлам, скрывающая их реальный источник (файловая система диска, встроенные в сборку ресурсы, память и т.д.) за единым интерфейсом. Например, `IWebHostEnvironment.WebRootFileProvider` даёт доступ к содержимому `wwwroot` через такую абстракцию — это то, чем внутри пользуется middleware `UseStaticFiles`, чтобы находить и отдавать статические файлы, не завязываясь напрямую на конкретную файловую систему.

**13) Как получить путь к папке «wwwroot»?**
Через внедрённый в конструктор/метод сервис `IWebHostEnvironment` и его свойство `WebRootPath` — например: `env.WebRootPath` (возвращает абсолютный физический путь к папке `wwwroot` на диске сервера).

**14) Форма передает файл. В каком виде этот файл будет представлен на сервере?**
В виде объекта, реализующего интерфейс `IFormFile` (либо коллекции `IFormFileCollection`/`Request.Form.Files`, если файлов несколько) — то есть не как "сырые байты в параметре", а как структурированный объект с метаданными файла и доступом к его содержимому через поток.

**15) Какой атрибут нужно установить в тэге `<form>`, чтобы можно было передавать файлы?**
`enctype="multipart/form-data"` (вместе с обязательным `method="post"` — передача файлов через `GET` невозможна).
