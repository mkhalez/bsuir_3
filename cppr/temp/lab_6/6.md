# Лабораторная работа №6. Аутентификация и авторизация — теория для защиты

Проект: `WebApplication1/` — `labs` (UI, MVC + Razor Pages, `https://localhost:7001`),
`labs.API` (REST API, `https://localhost:7002`), `labs.Domain` (сущности).
Сервер аутентификации — Keycloak в Docker (`http://localhost:8080`, Realm `Mikhalko`,
клиент `MikhalkoUiClient`), БД — Postgres. Схема: Клиент → Keycloak (login/token) →
Клиент с токеном → API → API проверяет токен у Keycloak (по metadata).

## 1. Аутентификация vs авторизация

- **Аутентификация (Authentication)** — установить, кто пользователь (проверка логина/пароля,
  валидация токена). В ASP.NET Core — middleware `app.UseAuthentication()`, которое по запросу
  строит `HttpContext.User` (объект `ClaimsPrincipal`).
- **Авторизация (Authorization)** — решить, можно ли аутентифицированному пользователю действие
  (роли, политики, Claims). Middleware `app.UseAuthorization()`, атрибуты `[Authorize]`,
  `RequireAuthorization("admin")`, `AllowAnonymous()`.
- Порядок в `Program.cs` всегда: `UseAuthentication()` затем `UseAuthorization()`
  (у нас так и в `labs.API/Program.cs:57-58`, и в `labs/Program.cs:60-62`).
  Без первого второе не знает, кто пришел.

## 2. Claims-модель: Claim, ClaimsIdentity, ClaimsPrincipal

- `Claim` — одно утверждение о пользователе: пара `Type/Value`
  (например `preferred_username = admin0606@mail.ru`, `avatar = /images/xxx.jpg`, `role = POWER-USER`).
- `ClaimsIdentity` — набор claims + указание схемы аутентификации (cookie, keycloak, Bearer).
- `ClaimsPrincipal` — пользователь целиком (`HttpContext.User`), содержит одну или несколько Identity.
- Проверка входа: `User.Identity.IsAuthenticated` (так делает `_UserInfoPartial`).
- Чтение: `User.Claims.FirstOrDefault(c => c.Type == "preferred_username")?.Value`,
  Id обычно `ClaimTypes.NameIdentifier` / `sub`. Аватар у нас — кастомный claim `avatar`.

## 3. Схемы, использованные в лабе

- Встроенный механизм ASP.NET Core — **cookie + JWT Bearer + OpenID Connect** (NuGet
  `Microsoft.AspNetCore.Authentication.JwtBearer`, `...OpenIdConnect`).
- **API (`labs.API`)**: только `AddAuthentication(JwtBearerDefaults.AuthenticationScheme).AddJwtBearer(...)`.
  API не логинит, а лишь валидирует присланный `Authorization: bearer <JWT>`:
  `MetadataAddress = {Host}/realms/{Realm}/.well-known/openid-configuration`,
  `Authority = {Host}/realms/{Realm}`, `Audience = "account"`, `RequireHttpsMetadata = false`
  (только для локального http-Keycloak). Плюс диагностика `JwtBearerEvents` (у нас пишет
  `JWT FAILED / JWT CHALLENGE` в консоль).
- **UI (`labs`)**: `DefaultScheme = Cookie`, `DefaultChallengeScheme = "keycloak"`,
  `.AddCookie()` + `.AddOpenIdConnect("keycloak", ...)` с `ResponseType = Code`
  (Authorization Code Flow), `Scope openid`, `SaveTokens = true` (иначе `GetTokenAsync("access_token")`
  вернет null), `RequireHttpsMetadata = false`, `UseTokenLifetime = true`.
  Неаутентифицированный заход на `/Admin/...` (Razor Pages, `MapRazorPages().RequireAuthorization("admin")`)
  делает Challenge → редирект на страницу `Sign in to Keycloak`.

## 4. Keycloak: Realm, Clients, Scopes, роли, мапперы

- **Realm** — изолированный домен безопасности (пользователи, клиенты, роли, настройки логина).
  У нас свой Realm `Mikhalko` (у `master` — только встроенный `admin`). Конечные точки Realm
  смотрятся в `Realm Settings > OpenID Endpoint Configuration`.
- **Clients** — приложения, говорящие с Keycloak (создаются внутри Realm).
  Наш `MikhalkoUiClient` типа OpenID Connect: `Client authentication = ON`,
  `Authorization = ON`, `Service accounts roles` (для `client_credentials`), Valid redirect URI
  на `https://localhost:7001/*`. Секрет — `Clients > Credentials` → лежит в `labs/appsettings.json`.
- **API scope** — область доступа, запрашиваемая клиентом (`openid` минимум;
  в коде `options.Scope.Add("openid")`).
- **Роли**: кастомная роль `POWER-USER` (`Realm roles > Add`), назначается
  администратору (`Users > Role Mapping`). В токен пробрасывается маппером:
  `Client scopes > roles > Mappers > By configuration > User client role`,
  `Token claim name = role`, `Multivalued = ON`, `Add to access token = ON`.
- **Атрибут avatar**: `Realm Settings > User Profile` — добавлен необязательный атрибут `avatar`;
  в токен проброшен маппером `ClientScopes > MikhalkoUiClient-dedicated > Add mapper > By configuration > User Attribute`,
  attribute `avatar`. Имя/фамилия (`FirstName/LastName`) из профиля удалены, логин — email
  (`Login > Email as username = ON`).
- **Service Account + `manage-users`**: чтобы UI мог создавать пользователей через Admin API,
  сервисному аккаунту клиента (`Clients > Service account roles`) назначена роль
  `realm-management > manage-users`. Без нее `POST /admin/realms/{realm}/users` отвечает `403`
  (мы это реально ловили: токен `200`, создание `403`).
- **Token endpoint**: `{Host}/realms/{Realm}/protocol/openid-connect/token`.
  Пользовательский токен: `grant_type=password (+username/password)`, клиентский:
  `grant_type=client_credentials (+client_id/client_secret)`.
- **Admin API создания пользователя**: `POST /admin/realms/{realm}/users` c
  `Authorization: bearer <client-token>` и JSON `UserRepresentation`
  (`username=email, email, enabled=true, emailVerified=true, attributes={avatar}, credentials=[{type=password,...}]`).

## 5. Политика `admin` и защита API

В обоих проектах:
```csharp
builder.Services.AddAuthorization(opt =>
    opt.AddPolicy("admin", p => p.RequireRole("POWER-USER")));
```
Роль прилетает из JWT как claim `role` (см. маппер выше).
В `labs.API/EndPoints/DishEndpoints.cs:16-31`: вся группа `/api/Dish`
`.RequireAuthorization("admin")`, а список `MapGet("/{category?}")` — `.AllowAnonymous()`.
Итог: читать каталог могут все, `GET by id / POST / PUT / DELETE` — только `POWER-USER`
(без токена — `401`, что проверяли в Insomnia/Postman добавлением заголовка `bearer`).

## 6. Токены в UI: ITokenAccessor / KeycloakTokenAccessor

`labs/Services/Authentication/`:
- `ITokenAccessor.SetAuthorizationHeaderAsync(HttpClient, bool isClient)` ставит
  `Authorization: bearer <token>`.
- Токен пользователя (`isClient:false`): из `HttpContext` (`AddHttpContextAccessor` +
  `await context.AuthenticateAsync("keycloak")` + `context.GetTokenAsync("keycloak","access_token")`).
  Если не вошли — `AuthenticationFailureException("Пользователь неавторизован")`.
- Токен клиента (`isClient:true`): `POST {Host}/realms/{Realm}/protocol/openid-connect/token`
  с `client_id/grаnt_type=client_credentials/client_secret`, парсинг `access_token` из JSON.
- Регистрация DI: `AddHttpClient<ITokenAccessor, KeycloakTokenAccessor>()`.
- Использование: `ApiProductService` перед каждым запросом вызывает его с `false`;
  список при отсутствии токена идет без заголовка, create/update/delete/getById без токена
  возвращают ошибку/логируют (иначе API даст `401`).

## 7. Своя регистрация (п. 4.8) — почему не страница Keycloak

У Keycloak есть встроенная страница регистрации, но она не умеет загружать файл картинки.
Поэтому: своя форма `GET /Account/Register` + сохранение аватара локально
(`Services/FileService`: `IFileService.SaveFileAsync`, реализация `LocalFileService` —
случайное имя `Guid + extension`, папка `wwwroot/images`, возврат `/images/{file}`; без файла —
`/images/default-profile-picture.png`) + создание пользователя через Admin API
(`Models/RegisterUserViewModel`: Email/Password/Compare/Avatar;
`Controllers/AccountController POST Register`: клиентский токен → сохранить аватар →
`CreateUserModel/UserCredentials` → `JsonSerializer` с `CamelCase` → `StringContent json` →
`POST /admin/realms/{realm}/users` → успех `Redirect Home/Index`, иначе `BadRequest`).
DI: `AddScoped<IFileService, LocalFileService>()`, `AddHttpClient<AccountController>()`
(без второго — `Unable to resolve HttpClient`). Вьюха `Views/Account/Register.cshtml`
обязательно с `enctype="multipart/form-data"`, иначе `Avatar` всегда null.
Важные грабли с этой лабы: папка вьюх строго `Views/Account` (была опечатка `Acount` →
`View not found`); папка картинок `images` маленькими (на Linux `Images != images`);
`Attributes` по методичке `Dictionary<string,string>`, строгий Keycloak ждет массивы —
при `400` менять на `Dictionary<string,List<string>>`.

## 8. Login/Logout и меню (п. 4.9)

`AccountController`: `Login()` → `HttpContext.ChallengeAsync("keycloak", RedirectUri=Home/Index)`;
`Logout [HttpPost]` → `SignOutAsync(Cookie)` + `SignOutAsync("keycloak", RedirectUri=Home/Index)`.
`_UserInfoPartial`: `if (IsAuthenticated)` — корзина (`CartViewComponent`) + имя
(`preferred_username`) + аватар (`avatar`, fallback на дефолт) + `Logout` (`dropdown-item`,
внутри `asp-controller=Account asp-action=Logout`); `else` — `Login + Register`
(`navbar-nav ms-auto`, класс `nav-color` под темный навбар). Удаление пользователя в Keycloak
— не выход: кука остается, надо жать `Logout`.

## 9. Инфраструктура и отладка

`compose.yaml`: `postgres + pgadmin + keycloak:26.0.4` (`KC_DB=postgres`, `start-dev`, порт `8080`).
`postgres.env`: `POSTGRES_*`, `PGADMIN_*`, `KEYCLOAK_ADMIN=admin / 123456`.
Нюансы Keycloak 26: переменные `KEYCLOAK_ADMIN_*` устарели, актуальные
`KC_BOOTSTRAP_ADMIN_USERNAME/PASSWORD`; bootstrap-пароль действует только при первом создании
(том `postgres_data` переживает рестарты) — при потере пароля создавать
`kc.sh bootstrap-admin user --username temp-admin ...` и сбрасывать. БД `keycloak`
создавать в pgAdmin вручную. Порты: UI `7001/5001`, API `7002/5002`, Keycloak `8080`.
Проверка: токен в Postman/Insomnia → `access_token`; запрос к API с/без `bearer` → объект / `401`;
логи `JWT FAILED/CHALLENGE`, `ITokenAccessor → 200`, `Default → 403/201`.

## Контрольные вопросы

**1. Какой механизм аутентификации имеет встроенную поддержку в ASP.NET Core?**
Cookie-аутентификация (`AddCookie`), JWT Bearer (`AddJwtBearer`), OpenID Connect (`AddOpenIdConnect`),
плюс внешний каркас Identity. В лабе: API — JWT Bearer, UI — Cookie + OIDC.

**2. Что описывают классы ClaimsPrincipal и ClaimsIdentity?**
`ClaimsIdentity` — одна идентичность: набор `Claim` + схема (`AuthenticationType`).
`ClaimsPrincipal` (`HttpContext.User`) — пользователь: одна или несколько Identity
(у нас cookie + keycloak). Проверки/чтение — через них.

**3. Как подключить Middleware аутентификации и авторизации?**
`builder.Services.AddAuthentication(...).AddCookie().AddOpenIdConnect(...)` /
`.AddJwtBearer(...)`; `builder.Services.AddAuthorization(...)`;
в конвейере `app.UseAuthentication(); app.UseAuthorization();` строго в этом порядке,
до `MapControllerRoute/MapRazorPages`.

**4. Пример использования HttpContext.User.**
`User.Identity.IsAuthenticated`, `User.Claims.FirstOrDefault(c => c.Type == "preferred_username")?.Value`
(так в `_UserInfoPartial`), `[Authorize(Roles=...)]`, в API — автоматическая проверка Bearer.

**5. Как в коде проверить, что пользователь прошел аутентификацию?**
`if (User.Identity?.IsAuthenticated ?? false)` (вьюха) или
`(await HttpContext.AuthenticateAsync("keycloak"))?.Principal != null` (как в `GetUserToken`).

**6. Как получить значение Claim пользователя?**
`User.FindFirst("avatar")?.Value` или LINQ по `User.Claims` с `StringComparison.OrdinalIgnoreCase`
(у нас для `preferred_username` и `avatar`).

**7. Как получить Id пользователя, прошедшего аутентификацию?**
`User.FindFirstValue(ClaimTypes.NameIdentifier)` (или `sub` в JWT). В Keycloak это GUID из `Users`.

**8. Как разрешить доступ к контроллеру только для пользователей с ролью «manager»?**
`[Authorize(Roles = "manager")]` или политика `opt.AddPolicy("m", p => p.RequireRole("manager"))` +
`[Authorize(Policy = "m")]` / `RequireAuthorization("m")` (у нас так с `admin`/`POWER-USER`).

**9. Как создать политику авторизации с помощью Claim?**
`AddAuthorization(opt => opt.AddPolicy("admin", p => p.RequireRole("POWER-USER")))` —
требование claim `role=POWER-USER`; или `RequireClaim("avatar")`, `RequireAuthenticatedUser()`.

**10. Как создать куки аутентификации с помощью HttpContext?**
В OIDC это делает handler сам (`AddCookie`, `SaveTokens=true`); вручную:
`await HttpContext.SignInAsync(CookieAuthenticationDefaults.AuthenticationScheme, principal)`,
удалить — `SignOutAsync(...)` (так в нашем `Logout`).

**11. Как добавить в проект использование Microsoft.AspNetCore.Identity?**
`dotnet add package Microsoft.AspNetCore.Identity.EntityFrameworkCore`,
`AddDbContext<AppIdentityDbContext>`, `AddIdentity<IdentityUser,IdentityRole>().AddEntityFrameworkStores<...>()`,
`app.UseAuthentication/UseAuthorization`, скаффолд `Areas/Identity`. В лабе вместо Identity —
внешний Keycloak (по заданию).

**12. Как с помощью Identity создать нового пользователя?**
`var r = await _userManager.CreateAsync(new IdentityUser{UserName=email,Email=email}, password);`
Аналог в лабе — `POST /admin/realms/{realm}/users` с `UserRepresentation` + `credentials`.

**13. Как с помощью Identity осуществить вход?**
`await _signInManager.PasswordSignInAsync(user, password, isPersistent:false, lockoutOnFailure:false);`
Аналог в лабе — Challenge к Keycloak (`Login()`) либо `grant_type=password` к token endpoint.

**14. Как с помощью Identity добавить Claim пользователю?**
`await _userManager.AddClaimAsync(user, new Claim("avatar", url));`
Аналог в лабе — положить `attributes.avatar` в `CreateUserModel` и маппер `User Attribute → avatar` в токен.

**15. Какой интерфейс используется в Identity для доступа к хранилищу пользователей?**
`IUserStore<TUser>` (базовый; полные — `IUserPasswordStore<TUser>`, `IUserClaimStore<TUser>` и т.д.,
реализация по умолчанию `UserStore` в `Microsoft.AspNetCore.Identity.EntityFrameworkCore`).
