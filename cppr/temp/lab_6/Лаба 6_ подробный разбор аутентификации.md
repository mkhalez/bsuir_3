## 0. Главная идея на пальцах

Представь клуб с охраной.

- **Охранник на входе** (Keycloak) проверяет паспорт и выдаёт **браслет** (токен). Браслет содержит: имя, роль («VIP» или «гость»), фото.
- **Бар** (API) сам паспорта не проверяет. Он смотрит на браслет: настоящий ли (подпись охранника) и разрешено ли тебе то, что просишь.
- **Ты** (браузер/сайт) предъявляешь браслет в баре.

Всё, что мы делали в лабе, сводится к трём задачам:

1. Поставить и настроить охранника (Keycloak).
2. Научить бар проверять браслеты (проект API).
3. Научить сайт получать браслет и показывать его владельца (проект UI: вход, выход, регистрация).

## 1. Словарь простыми словами

| Термин | Что это на самом деле |
| --- | --- |
| **Аутентификация** | «Кто ты?» Проверка личности (логин+пароль или токен). |
| **Авторизация** | «Что тебе можно?» Проверка прав (роль, политика). |
| **Токен (JWT)** | Строка из трёх частей через точки. Внутри JSON с данными о пользователе и подпись Keycloak. Подделать нельзя: подпись не сойдётся. |
| **Claim** | Одно утверждение внутри токена: `preferred_username = admin@mail.ru`, `role = POWER-USER`, `avatar = /images/1.jpg`. |
| **ClaimsIdentity** | Набор claims одного «документа» (например, из куки). |
| **ClaimsPrincipal** | Пользователь целиком. Это и есть `HttpContext.User` / `User` во вьюхе. |
| **Realm** | Отдельный «мир» в Keycloak: свои пользователи, клиенты, роли. У тебя `Mikhalko`. `master` нужен только для админа Keycloak. |
| **Client** | Приложение, которому Keycloak доверяет. У тебя это сайт `MikhalkoUiClient`. |
| **Client secret** | Пароль самого приложения к Keycloak. |
| **Scope** | Какие данные запрашивает приложение (`openid`, `email`, `profile`). |
| **Role (роль)** | Метка пользователя. У тебя `POWER-USER` = админ сайта. |
| **Mapper** | Правило в Keycloak: «возьми такое-то поле и положи в токен как claim». |
| **Service account** | «Служебный пользователь» самого клиента. Нужен, чтобы приложение действовало от своего имени без человека. |
| **Cookie (кука)** | Маленький файл в браузере. Сайт кладёт туда факт «этот человек вошёл», чтобы не спрашивать пароль на каждой странице. |
| **Challenge** | Команда ASP.NET: «этот человек не вошёл, отправь его на страницу входа». |

## 2. Два вида токена

Это самое частое место непонимания. В лабе токены **двух разных видов**:

|  | Токен клиента | Токен пользователя |
| --- | --- | --- |
| От чьего имени | от имени **самого приложения** (service account) | от имени **человека** |
| Как получить | `grant_type=client_credentials` + `client_id` + `client_secret` | вход через страницу Keycloak (или `grant_type=password`) |
| Для чего у нас | **регистрация** новых пользователей (Admin API) | **запросы к API** (создать/изменить/удалить блюдо) |
| В коде | `GetClientToken()` | `GetUserToken()` |

Почему при регистрации нужен именно токен клиента? Человека ещё нет. Войти он не мог, поэтому от его имени ничего сделать нельзя. Сайт идёт к Keycloak от своего имени и говорит: «создай мне пользователя». Keycloak разрешает, только если у сайта есть право `manage-users`.

## 3. Общая схема: что с чем разговаривает

```
 Браузер ──(1) открыл /Admin──────────────► UI (labs :7001)
                                              │ не вошёл → Challenge
 Браузер ◄─(2) редирект на страницу входа──────┘
 Браузер ──(3) логин/пароль───────────────► Keycloak (:8080)
 Браузер ◄─(4) редирект назад + code───────  Keycloak
 UI      ──(5) обмен code на токены────────► Keycloak
 UI      ◄─(6) access_token (JWT)───────────  Keycloak
 UI сохраняет токены в куку (SaveTokens = true)

 Потом, когда админ жмёт «Создать блюдо»:
 UI ──(7) POST /api/Dish + Authorization: bearer <токен>──► API (:7002)
 API ──(8) проверяет подпись токена по ключам Keycloak────► Keycloak
 API ──(9) роль POWER-USER есть? да → выполняет, нет → 401/403
```

Что здесь нужно запомнить:

- Пароль человека видит **только Keycloak**. Ни UI, ни API его не знают.
- UI и API общаются не паролями, а токеном.
- API не «звонит» Keycloak на каждый запрос. Он один раз скачивает публичные ключи (по `MetadataAddress`) и дальше проверяет подпись сам.

## 4. Настройка Keycloak (по шагам, зачем каждый)

Это не код, а клики в админке `localhost:8080`. Ниже что делали и для чего.

### 4.1 Docker и база

Файл `compose.yaml` (раздел 1 твоего кода) запускает три контейнера: `postgres` (база), `pgadmin` (веб-управление базой) и `keycloak`.

```yaml
keycloak:
  image: quay.io/keycloak/keycloak:26.0.4
  command: start-dev          # режим разработки, http без сертификата
  environment:
    KC_DB: postgres           # хранить данные в Postgres
    KC_DB_URL_HOST: postgres  # имя контейнера с базой (в docker-сети по имени)
    KC_DB_URL_DATABASE: keycloak
    KC_DB_USERNAME / KC_DB_PASSWORD   # берутся из postgres.env
  ports: ["8080:8080"]
```

- Базу `keycloak` нужно создать вручную в pgAdmin. Сам Keycloak её не создаёт.
- Данные лежат в томе Docker. Они переживают перезапуск. Удалит их только `docker compose down -v`.
- `KEYCLOAK_ADMIN` и `KEYCLOAK_ADMIN_PASSWORD` в Keycloak 26 помечены устаревшими. Актуальные имена `KC_BOOTSTRAP_ADMIN_USERNAME/PASSWORD`. Эти пароли действуют только при самом первом запуске. Поэтому у тебя жёлтая плашка «temporary admin user».

### 4.2 Realm `Mikhalko`

Realm создали, чтобы не работать в `master`. Включили **Email as username** и **Login with email**, чтобы логином служил email.

В **User Profile** удалили `firstName` и `lastName` (по заданию они не нужны). Добавили необязательный атрибут **`avatar`** с правами edit/view для User и Admin. Без него Keycloak не сохранил бы адрес картинки.

### 4.3 Client `MikhalkoUiClient`

Что включали и зачем:

| Настройка | Зачем |
| --- | --- |
| Client authentication = ON | у приложения есть секрет (оно «конфиденциальное») |
| Authorization = ON | по методичке |
| Standard flow | вход по схеме «Authorization Code» (редирект на страницу Keycloak). Именно её использует `AddOpenIdConnect` |
| Direct access grants | разрешает `grant_type=password`. Нужно для проверки токена в Postman |
| Service accounts roles | разрешает `grant_type=client_credentials` и создаёт служебного пользователя |
| Valid redirect URIs = `https://localhost:7001/*` | Keycloak вернёт человека только на этот адрес. Иначе ошибка «Invalid redirect uri» |
| Root URL / Web origins | адрес твоего сайта |

### 4.4 Роль `manage-users` для service account

`Clients → MikhalkoUiClient → Service accounts roles → Assign role → realm-management → manage-users`.

Это право создавать пользователей через Admin API. Без него `POST /admin/realms/Mikhalko/users` возвращает **403**. Мы это ловили на практике.

### 4.5 Mapper для `avatar`

`Clients → MikhalkoUiClient → Client scopes → MikhalkoUiClient-dedicated → Add mapper → By configuration → User Attribute`:

- User Attribute = `avatar`
- Token Claim Name = `avatar`
- Add to ID token = ON, Add to access token = ON

Без него атрибут лежал бы в Keycloak, но в токен не попал бы. Тогда `_UserInfoPartial` не нашёл бы `avatar` среди claims.

### 4.6 Роль `POWER-USER` и mapper для неё

Роль `POWER-USER` по методичке создаётся на вкладке **Roles клиента** `MikhalkoUiClient` (`Clients → MikhalkoUiClient → Roles`). Это **client role**. Назначают её админу: `Users → <админ> → Role mapping`.

Потом в `Client scopes → roles → Mappers` добавили mapper **User Client Role**:

- Token Claim Name = **`role`**
- Multivalued = ON
- Add to access token = ON (и желательно Add to ID token = ON, потому что UI читает claims из ID-токена)

Итог: в токене админа появляется `"role": ["POWER-USER", ...]`. Политика `admin` ищет именно её.

> **Проверь у себя.** В твоём отчёте написано «`Realm roles > Add`». Mapper «User Client Role» берёт только роли **клиента**, а не роли Realm. Если `POWER-USER` создана как realm role, в claim `role` она не попадёт, и админ не получит доступ. Создавать надо в `Clients → MikhalkoUiClient → Roles`. На скриншоте JWT в методичке это видно: `resource_access → LabsUiClient → roles → POWER-USER`.

### 4.7 Ошибка, которую мы поймали (стандартный mapper `client roles`)

В Client scope `roles` уже есть **стандартный** mapper `client roles` с Token Claim Name `resource_access.${client_id}.roles` и пустым Client ID. Его **нельзя** переделывать под свой `role`. Когда его испортили, токен клиента остался без блока `resource_access.realm-management.roles = [manage-users]`. Keycloak не увидел права и отвечал **403**.

Правило: свой mapper создавай **новым** (`By configuration`), стандартные не трогай.

### 4.8 Проверка в Postman/Insomnia/curl

Адрес: `http://localhost:8080/realms/Mikhalko/protocol/openid-connect/token` (точный адрес смотри в Realm settings → OpenID Endpoint Configuration → `token_endpoint`).

- Токен человека: `client_id`, `client_secret`, `grant_type=password`, `username`, `password`.
- Токен клиента: `client_id`, `client_secret`, `grant_type=client_credentials`.

В ответе `access_token`. Вставь его на `jwt.io` и посмотри claims. Так проверяют, что `role`, `avatar` и `resource_access` на месте.

## 5. Проект API (`labs.API`): как он проверяет токены

### 5.1 Что делает API

API **никого не логинит**. Он принимает запрос с заголовком `Authorization: bearer <JWT>`, проверяет токен и решает, пускать ли.

### 5.2 `appsettings.json` и класс `AuthServerData` (разделы 4–5 кода)

```json
"AuthServer": { "Host": "http://localhost:8080", "Realm": "Mikhalko" }
```

```csharp
internal class AuthServerData { public string Host {get;set;} public string Realm {get;set;} }
```

Это только способ не хардкодить адрес. `Get<AuthServerData>()` читает секцию из конфигурации и превращает её в объект.

### 5.3 `Program.cs` (раздел 6 кода) по строкам

```csharp
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(JwtBearerDefaults.AuthenticationScheme, o => { ... });
```

«Для проверки входящих запросов используй схему JWT Bearer».

| Строка | Смысл |
| --- | --- |
| `MetadataAddress = .../.well-known/openid-configuration` | Откуда API берёт описание сервера: где публичные ключи для проверки подписи, кто издатель |
| `Authority = .../realms/Mikhalko` | Кто должен был выдать токен. Токен от другого издателя будет отвергнут |
| `Audience = "account"` | Для кого токен. Keycloak по умолчанию ставит `aud: account`. Токен «не для нас» будет отвергнут |
| `RequireHttpsMetadata = false` | Разрешить `http` для локального Keycloak. В продакшене должно быть `true` |
| `Events` | Наша отладка: в консоль пишет `JWT FAILED` и `JWT CHALLENGE`, если токен не прошёл |

```csharp
builder.Services.AddAuthorization(opt =>
    opt.AddPolicy("admin", p => p.RequireRole("POWER-USER")));
```

Создаём **политику** `admin`: «пускать только тех, у кого роль `POWER-USER`». Роль берётся из claim `role` в токене (поэтому в Keycloak делали mapper с именем `role`).

```csharp
app.UseAuthentication();   // 1. сначала выясни, КТО пришёл
app.UseAuthorization();    // 2. потом реши, МОЖНО ли ему
```

Порядок строгий. Если поменять местами, авторизация не будет знать, кто пользователь.

### 5.4 Защита эндпоинтов (раздел 7 кода)

```csharp
var group = routes.MapGroup("/api/Dish")
    .DisableAntiforgery()
    .RequireAuthorization("admin");     // ВСЯ группа только для admin

group.MapGet("/{category:alpha?}", ...)
    .AllowAnonymous();                  // исключение: список блюд видят все
```

Итог:

| Запрос | Без токена | Токен без роли | Токен POWER-USER |
| --- | --- | --- | --- |
| GET список блюд | 200 | 200 | 200 |
| GET блюдо по id | **401** | 403 | 200 |
| POST / PUT / DELETE | **401** | 403 | 200 |

**401** = «ты не представился» (нет токена или он плохой). **403** = «я тебя знаю, но тебе нельзя».

Двойная точка с запятой `;;` в твоём коде безвредна, но лишнюю можно убрать.

## 6. Проект UI (`labs`): вход, токены, защита страниц

### 6.1 Конфигурация (разделы 9–10 кода)

`appsettings.json` секция `Keycloak` содержит `Host`, `Realm`, `ClientId`, `ClientSecret`. Класс `KeycloakData` её описывает. В `HostingExtensions` стоит:

```csharp
builder.Services.Configure<KeycloakData>(builder.Configuration.GetSection("Keycloak"));
```

Теперь в любой класс можно внедрить `IOptions<KeycloakData>` и получить эти настройки.

> **Безопасность.** `ClientSecret` лежит прямо в `appsettings.json`, а ты показывал его в чате. Для учебного проекта терпимо. После сдачи нажми **Regenerate** в `Clients → MikhalkoUiClient → Credentials` и не коммить секрет в публичный репозиторий.

### 6.2 `Program.cs` UI (раздел 11 кода) по строкам

```csharp
.AddAuthentication(options => {
    options.DefaultScheme = CookieAuthenticationDefaults.AuthenticationScheme;
    options.DefaultChallengeScheme = "keycloak";
})
```

- **DefaultScheme = Cookie**: в обычной жизни сайт узнаёт человека по куке.
- **DefaultChallengeScheme = "keycloak"**: если нужно потребовать вход, использовать схему `keycloak`, то есть отправить на страницу Keycloak.

```csharp
.AddCookie()
.AddOpenIdConnect("keycloak", options => { ... })
```

Две схемы работают вместе. OpenID Connect (OIDC) умеет разговаривать с Keycloak. Cookie хранит результат входа.

| Опция | Смысл |
| --- | --- |
| `Authority` | Адрес Realm. Важно: `.../realms/Mikhalko`. В методичке написано `/auth/realms/...`, но это устаревший адрес, для Keycloak 26 он неверный |
| `ClientId`, `ClientSecret` | Данные клиента из Keycloak |
| `ResponseType = Code` | Authorization Code Flow: Keycloak возвращает одноразовый код, UI меняет его на токены напрямую (безопаснее) |
| `Scope.Add("openid")` | Минимальный scope для OIDC |
| `SaveTokens = true` | Сохранить токены в куке. **Без этого** `GetTokenAsync("access_token")` вернёт `null`, и UI не сможет обратиться к API |
| `RequireHttpsMetadata = false` | Разрешить http для локального Keycloak |
| `MetadataAddress` | Где лежит описание сервера |
| `UseTokenLifetime = true` | Срок жизни куки равен сроку жизни токена |

```csharp
builder.Services.AddAuthorization(opt =>
    opt.AddPolicy("admin", p => p.RequireRole("POWER-USER")));
...
app.UseAuthentication();
app.UseAuthorization();
app.MapRazorPages().RequireAuthorization("admin");
```

Последняя строка: **все Razor Pages** (раздел «Администрирование», `/Admin/...`) только для `admin`. Если зайти без входа, сработает Challenge, и тебя отправит на страницу Keycloak. Если вошёл, но без роли, получишь «Access denied».

### 6.3 `ITokenAccessor` и `KeycloakTokenAccessor` (разделы 13–14 кода)

Это «кладовщик токенов». Его задача: положить в `HttpClient` заголовок `Authorization: bearer ...`.

```csharp
Task SetAuthorizationHeaderAsync(HttpClient httpClient, bool isClient);
```

`isClient = true` значит «нужен токен приложения», `false` значит «токен текущего человека».

**Токен человека (`GetUserToken`)**

```csharp
var context = contextAccessor.HttpContext ...;
var authSession = await context.AuthenticateAsync("keycloak");
if (authSession?.Principal == null) throw new AuthenticationFailureException("Пользователь неавторизован");
return await context.GetTokenAsync("keycloak", "access_token") ...;
```

1. Через `IHttpContextAccessor` берём текущий HTTP-запрос. Для этого в `Program` есть `AddHttpContextAccessor()`.
2. Проверяем, вошёл ли человек.
3. Достаём его `access_token`, который сохранила кука благодаря `SaveTokens = true`.

**Токен клиента (`GetClientToken`)**

```csharp
POST {Host}/realms/{Realm}/protocol/openid-connect/token
  client_id=..., grant_type=client_credentials, client_secret=...
```

Читаем `access_token` из JSON-ответа. Если ответ не 2xx, бросаем исключение.

Регистрация в DI:

```csharp
builder.Services.AddHttpClient<ITokenAccessor, KeycloakTokenAccessor>();
```

Так в `KeycloakTokenAccessor` попадает свой `HttpClient`.

### 6.4 `ApiProductService` (раздел 15 кода)

Сервис, который ходит из UI в API. Перед каждым запросом он вызывает:

```csharp
await _tokenAccessor.SetAuthorizationHeaderAsync(_httpClient, false);
```

Особенности:

- **Список блюд**: если токена нет (человек не вошёл), мы не падаем. Пишем в лог и убираем заголовок: `Authorization = null`. Список в API доступен анонимно.
- **Создать / получить по id**: без токена возвращаем `ResponseData.Error(...)`.
- **Изменить / удалить**: без токена пишем в лог и выходим. Иначе API ответил бы 401.

## 7. Регистрация: зачем нужен `/Account/Register`

Это твой вопрос из начала разговора.

### 7.1 Зачем своя страница

У Keycloak есть своя страница регистрации, но она **не умеет загружать файл** аватара. Задание требует аватар. Поэтому:

1. Делаем свою форму на сайте (`/Account/Register`).
2. Сохраняем картинку себе на диск.
3. Создаём пользователя в Keycloak через **Admin API**, а путь к картинке пишем в атрибут `avatar`.
4. Mapper (раздел 4.5) кладёт `avatar` в токен, и меню показывает картинку.

Кнопка **Register** в шапке ведёт именно на `/Account/Register`. Без неё страница регистрации недоступна.

### 7.2 Сохранение файла (разделы 16–17 кода)

```csharp
var ext = Path.GetExtension(file.FileName);          // ".png"
var fileName = $"{Guid.NewGuid()}{ext}";             // "3f2c...-...png" (случайное имя)
var imagesDir = Path.Combine(environment.WebRootPath, "images");   // wwwroot/images
Directory.CreateDirectory(imagesDir);                // создать папку, если нет
await using var stream = File.Create(filePath);
await file.CopyToAsync(stream);                      // записать файл
return $"/images/{fileName}";                        // адрес для браузера
```

`Guid.NewGuid()` даёт уникальное имя. Так два файла с одинаковым названием не перезапишут друг друга. Папку называем `images` с маленькой буквы, потому что на Linux `Images` и `images` разные папки.

### 7.3 Модель формы (раздел 18 кода)

```csharp
[Required] [EmailAddress] string Email
[Required] [DataType(DataType.Password)] string Password
[Required] [Compare(nameof(Password))] string ConfirmPassword   // должен совпасть с Password
IFormFile? Avatar                                              // файл, необязательный
```

Атрибуты — это валидация. `ModelState.IsValid` в контроллере проверяет, что всё заполнено верно.

### 7.4 Контроллер `AccountController.Register` (раздел 19 кода) по шагам

```csharp
public IActionResult Register() => View(new RegisterUserViewModel());   // GET: показать форму
```

```csharp
[HttpPost] [AutoValidateAntiforgeryToken]
public async Task<IActionResult> Register(RegisterUserViewModel user)   // POST: принять форму
```

`AutoValidateAntiforgeryToken` защищает форму от подделки запросов с чужих сайтов (CSRF). Токен автоматически вставляется в форму тег-хелпером.

Шаги внутри:

1. `if (!ModelState.IsValid) return View(user);` Если поля заполнены неверно, показываем форму снова с ошибками.
2. `SetAuthorizationHeaderAsync(httpClient, true)` Берём **токен клиента** и вешаем его на `httpClient`. Если не вышло, возвращаем `Unauthorized()` (401).
3. Аватар: по умолчанию `/images/default-profile-picture.png`. Если файл загружен, сохраняем и берём его адрес.
4. Собираем `CreateUserModel`:
   - `Attributes["avatar"]` = адрес картинки
   - `Username` = `Email` = введённый email
   - `Credentials` = пароль (`Temporary = false`, чтобы не требовали сменить)
   - `Enabled = true`, `EmailVerified = true` (не нужно подтверждать почту)
5. Сериализуем в JSON с `CamelCase` (`Username` → `username`), потому что Keycloak ждёт маленькие первые буквы.
6. `POST {Host}/admin/realms/{Realm}/users` с JSON.
7. Успех (`201 Created`) → `Redirect` на `Home/Index`. Иначе `BadRequest(response.StatusCode)`.

**Что означают коды при регистрации:**

| Код | Причина |
| --- | --- |
| Редирект на главную | успех |
| 400 | пользователь с таким email уже есть, либо неверный формат JSON/атрибутов |
| 401 (от твоего контроллера) | не удалось получить токен клиента: неверный `ClientSecret` или Keycloak недоступен |
| **403** | у токена клиента **нет права `manage-users`** в токене (разделы 4.4 и 4.7) |
| 409 | пользователь уже существует |

Совет для отладки: временно верни в `BadRequest` тело ответа Keycloak:

```csharp
var body = await response.Content.ReadAsStringAsync();
return BadRequest($"{(int)response.StatusCode}: {body}");
```

Классы `UserCredentials` и `CreateUserModel` лежат в том же файле, потому что больше нигде не нужны.

DI для контроллера (раздел 12 кода):

```csharp
builder.Services.AddScoped<IFileService, LocalFileService>();
builder.Services.AddHttpClient<AccountController>();   // иначе: Unable to resolve HttpClient
```

## 8. Вход, выход и меню (п. 4.9)

### 8.1 Login и Logout (раздел 19 кода)

```csharp
public async Task Login() =>
    await HttpContext.ChallengeAsync("keycloak",
        new AuthenticationProperties { RedirectUri = Url.Action("Index", "Home") });
```

«Перебрось на страницу Keycloak. После входа вернись на `Home/Index`». Это единственное, что делает Login, а проверкой пароля занимается Keycloak.

```csharp
[HttpPost]
public async Task Logout()
{
    await HttpContext.SignOutAsync(CookieAuthenticationDefaults.AuthenticationScheme); // стереть нашу куку
    await HttpContext.SignOutAsync("keycloak", new AuthenticationProperties { RedirectUri = ... }); // завершить сессию в Keycloak
}
```

Выход делаем двумя шагами: удаляем куку на сайте **и** закрываем сессию в Keycloak. Метод `HttpPost`, потому что выход меняет состояние, а ссылками (GET) такие вещи делать нельзя. Поэтому в меню Logout — это форма с кнопкой.

Чтобы после выхода не появлялась ошибка «Invalid redirect uri», в `Clients → MikhalkoUiClient → Settings → Valid post logout redirect URIs` добавь `https://localhost:7001/*`.

Важно: удалить пользователя в Keycloak не значит выйти. Кука на сайте остаётся, пока не нажмёшь Logout.

### 8.2 `_UserInfoPartial.cshtml` (раздел 21 кода)

```csharp
var name = User.Claims.FirstOrDefault(c => c.Type.Equals("preferred_username", OrdinalIgnoreCase))?.Value;
var avatar = User.Claims.FirstOrDefault(c => c.Type.Equals("avatar", OrdinalIgnoreCase))?.Value;
if (string.IsNullOrEmpty(avatar)) avatar = "/images/default-profile-picture.png";
```

`User` — это `ClaimsPrincipal`. Из его claims достаём имя (`preferred_username`) и аватар. Если аватара нет, подставляем стандартный.

Логика:

```
if (вошёл)  → корзина + выпадающее меню (имя, аватар, Logout)
else        → ссылки Login и Register
```

Ссылки используют тег-хелперы `asp-controller="Account" asp-action="Login"`. Они сами строят адрес `/Account/Login`.

Класс `nav-color` и `navbar-nav ms-auto` нужны, чтобы ссылки были видны на тёмной шапке. Без цвета текст сливается с фоном, и кажется, что кнопок нет. Это та проблема, с которой ты начал.

## 9. Сценарии «от нажатия до результата»

### Сценарий А: регистрация

1. Нажал Register → `GET /Account/Register` → форма.
2. Заполнил, выбрал картинку → `POST /Account/Register` (multipart).
3. Контроллер: проверка модели → токен клиента → сохранение картинки в `wwwroot/images` → JSON → `POST` в Keycloak Admin API.
4. Keycloak создал пользователя (`201`) → редирект на главную.
5. Проверка: `Keycloak → Users → найти email`. Там `Email verified = ON`, атрибут `avatar`, в Credentials есть пароль.

### Сценарий Б: вход

1. Нажал Login → `GET /Account/Login` → Challenge → редирект на Keycloak.
2. Ввёл email и пароль в Keycloak.
3. Keycloak вернул на сайт с кодом; OIDC-handler обменял код на токены, положил в куку (`SaveTokens`).
4. `User.Identity.IsAuthenticated = true`, `_UserInfoPartial` показывает имя и аватар.

### Сценарий В: админ создаёт блюдо

1. `/Admin/...` → политика `admin`: вошёл ли и есть ли роль `POWER-USER`?
2. Форма «Create» → `ApiProductService.CreateProductAsync`.
3. `GetUserToken()` → токен из куки → заголовок `bearer`.
4. API проверяет токен и роль → создаёт блюдо.
5. Если зайти обычным пользователем (без роли), страницу не покажут.

## 10. Типичные ошибки и их причины

| Симптом | Причина | Решение |
| --- | --- | --- |
| Нет кнопок Login/Register | Нет цвета у ссылок на тёмном фоне или partial не вызывается без входа | `nav-color`/`text-light`; `<partial name="_UserInfoPartial" />` вызывать всегда |
| `403` при регистрации | У токена клиента нет `manage-users` | Service account roles + проверить `resource_access` в токене; не ломать mapper `client roles` |
| `401` при регистрации | Неверный `ClientSecret` / Keycloak не запущен | Сверить секрет в `Credentials` и `appsettings.json` |
| `400` при регистрации | Email уже есть или Keycloak не принял атрибуты | Другой email; смотреть тело ответа. Если ругается на `attributes`, сменить тип на `Dictionary<string, List<string>>` |
| `View not found` | Папка вьюх названа неверно | Строго `Views/Account` |
| `Unable to resolve HttpClient` | Нет `AddHttpClient<AccountController>()` | Добавить в DI |
| `Avatar` всегда `null` | Нет `enctype="multipart/form-data"` | Добавить в форму |
| `access_token` равен `null` | Нет `SaveTokens = true` | Включить |
| Admin видит «Access denied» | Нет claim `role = POWER-USER` | Роль клиента (не realm), mapper `role`, Add to ID token |
| API даёт 401 с токеном | Не тот `Audience`/`Authority` или токен просрочен (5 минут) | Смотреть консоль `JWT FAILED` |
| «Invalid redirect uri» | Нет адреса в Valid (post logout) redirect URIs | Добавить `https://localhost:7001/*` |
| Картинка не открывается на Linux | `Images` и `images` — разные папки | Везде `images` |

## 11. Ответы на контрольные вопросы

**1. Какой механизм аутентификации имеет встроенную поддержку в ASP.NET Core?** Встроенная поддержка есть у трёх схем: **Cookie** (`AddCookie`), **JWT Bearer** (`AddJwtBearer`), **OpenID Connect** (`AddOpenIdConnect`). Дополнительно есть система членства **ASP.NET Core Identity**. Все они работают через подсистему `Microsoft.AspNetCore.Authentication` с понятием «схема аутентификации». В лабе: API использует JWT Bearer, UI использует Cookie + OpenID Connect.

**2. Что описывают классы ClaimsPrincipal и ClaimsIdentity?** `Claim` — одно утверждение о пользователе (тип + значение). `ClaimsIdentity` — один «документ» пользователя: набор claims плюс тип аутентификации (cookie, keycloak, Bearer). `ClaimsPrincipal` — сам пользователь, содержит одну или несколько `ClaimsIdentity`. Именно `ClaimsPrincipal` доступен как `HttpContext.User` и как `User` во вьюхах и контроллерах.

**3. Как подключить Middleware аутентификации и авторизации?** Сначала регистрируем сервисы:

```csharp
builder.Services.AddAuthentication(...).AddCookie().AddOpenIdConnect(...);   // или .AddJwtBearer(...)
builder.Services.AddAuthorization(...);
```

Потом в конвейере, строго в таком порядке и до `MapControllerRoute`/`MapRazorPages`:

```csharp
app.UseAuthentication();
app.UseAuthorization();
```

**4. Приведите пример использования свойства HttpContext.User.** В нашем `_UserInfoPartial`: `User.Claims.FirstOrDefault(c => c.Type == "preferred_username")?.Value` — получить имя; `User.Identity.IsAuthenticated` — проверить вход. В контроллере: `var name = User.Identity?.Name;` или `User.IsInRole("POWER-USER")`.

**5. Как в коде проверить, что пользователь прошёл аутентификацию?** `User.Identity?.IsAuthenticated ?? false` (так во вьюхе). Или явно по схеме: `(await HttpContext.AuthenticateAsync("keycloak"))?.Principal != null` (так в `GetUserToken`). Или атрибутом `[Authorize]`, который сам не пустит неаутентифицированного.

**6. Как получить значение Claim пользователя?**

```csharp
var avatar = User.FindFirst("avatar")?.Value;
// или через LINQ (как у нас):
User.Claims.FirstOrDefault(c => c.Type.Equals("avatar", StringComparison.OrdinalIgnoreCase))?.Value;
```

**7. Как получить Id пользователя, прошедшего аутентификацию?**

```csharp
var id = User.FindFirstValue(ClaimTypes.NameIdentifier);
```

В JWT от Keycloak это claim `sub` (GUID пользователя, виден в `Users`). В зависимости от настроек маппинга claims он может называться `sub` или `NameIdentifier`.

**8. Как разрешить доступ к контроллеру только для пользователей с ролью «manager»?** Атрибутом: `[Authorize(Roles = "manager")]` над контроллером или действием. Или через политику: `AddPolicy("m", p => p.RequireRole("manager"))` и `[Authorize(Policy = "m")]` (для minimal API `.RequireAuthorization("m")`). У нас так сделано с политикой `admin` и ролью `POWER-USER`.

**9. Как создать политику авторизации с помощью Claim?**

```csharp
builder.Services.AddAuthorization(opt =>
{
    opt.AddPolicy("HasAvatar", p => p.RequireClaim("avatar"));                  // claim должен быть
    opt.AddPolicy("Vip", p => p.RequireClaim("level", "gold", "platinum"));     // с одним из значений
    opt.AddPolicy("admin", p => p.RequireRole("POWER-USER"));                   // роль — это тоже claim
});
```

Применяем: `[Authorize(Policy = "Vip")]`.

**10. Как создать куки аутентификации с помощью объекта HttpContext?** Собрать `ClaimsPrincipal` и войти:

```csharp
var claims = new List<Claim> { new(ClaimTypes.Name, "user@mail.ru"), new(ClaimTypes.Role, "manager") };
var identity = new ClaimsIdentity(claims, CookieAuthenticationDefaults.AuthenticationScheme);
await HttpContext.SignInAsync(CookieAuthenticationDefaults.AuthenticationScheme, new ClaimsPrincipal(identity));
```

Удаление: `await HttpContext.SignOutAsync(CookieAuthenticationDefaults.AuthenticationScheme);` (так в нашем `Logout`). В лабе куку создаёт OIDC-handler автоматически после возврата от Keycloak.

**11. Как добавить в проект использование системы членства Microsoft.AspNetCore.Identity?**

1. Пакеты `Microsoft.AspNetCore.Identity.EntityFrameworkCore` и провайдер БД.
2. Класс контекста `AppDbContext : IdentityDbContext<IdentityUser>`.
3. Регистрация:

```csharp
builder.Services.AddDbContext<AppDbContext>(...);
builder.Services.AddIdentity<IdentityUser, IdentityRole>()
    .AddEntityFrameworkStores<AppDbContext>();
```

4. `app.UseAuthentication(); app.UseAuthorization();`
5. Миграция и обновление БД; при желании скаффолд страниц `Areas/Identity`. В нашей лабе Identity не используется: роль хранилища пользователей играет Keycloak.

**12. Как с помощью Identity создать нового пользователя?**

```csharp
var user = new IdentityUser { UserName = email, Email = email };
IdentityResult result = await _userManager.CreateAsync(user, password);
```

Аналог в лабе: `POST /admin/realms/{realm}/users` в Keycloak с JSON `username`, `email`, `credentials`.

**13. Как с помощью Identity осуществить вход пользователя в систему?**

```csharp
var result = await _signInManager.PasswordSignInAsync(email, password, isPersistent: false, lockoutOnFailure: false);
```

`SignInManager` проверяет пароль и выдаёт куку. Аналог в лабе: `Login()` с `ChallengeAsync("keycloak")` (вход на странице Keycloak) или запрос `grant_type=password` к token endpoint.

**14. Как с помощью Identity добавить Claim пользователю?**

```csharp
await _userManager.AddClaimAsync(user, new Claim("avatar", "/images/1.jpg"));
```

Аналог в лабе: атрибут `avatar` в Keycloak + mapper «User Attribute», который кладёт его в токен.

**15. Какой интерфейс используется в Identity для доступа к хранилищу пользователей?** `IUserStore<TUser>`. Это базовый интерфейс хранилища. Его расширяют специализированные: `IUserPasswordStore<TUser>`, `IUserClaimStore<TUser>`, `IUserRoleStore<TUser>`, `IUserEmailStore<TUser>` и т.д. Реализация по умолчанию для Entity Framework — класс `UserStore`. `UserManager` работает с хранилищем именно через эти интерфейсы.

## 12. Шпаргалка для защиты (30 секунд на каждое)

- **Что сделано?** Развернули Keycloak в Docker, настроили Realm `Mikhalko`, клиента, роль `POWER-USER`, мапперы `avatar` и `role`. API проверяет JWT, UI входит через Keycloak (Cookie + OIDC), админка и изменение данных только для роли `POWER-USER`, своя регистрация с аватаром через Admin API.
- **Почему Keycloak?** Готовый сервер аутентификации: страницы входа, выдача и проверка токенов, роли.
- **Что такое JWT?** Подписанный JSON с claims. Подпись нельзя подделать, API проверяет её публичным ключом Keycloak.
- **Чем отличаются токены клиента и пользователя?** Клиента получает приложение для регистрации, пользователя получает человек при входе, им обращаемся к API.
- **Почему при регистрации 403?** У service account нет `manage-users` (или она не попала в токен).
- **Почему без токена API отвечает 401?** Группа `/api/Dish` закрыта политикой `admin`, анонимно открыт только список.
- **Зачем `SaveTokens = true`?** Чтобы токен лежал в куке, и UI мог переслать его в API.
- **Зачем `UseAuthentication` раньше `UseAuthorization`?** Сначала определяем, кто пришёл, потом решаем, можно ли ему.
- **Зачем enctype multipart?** Иначе файл аватара не отправится.
